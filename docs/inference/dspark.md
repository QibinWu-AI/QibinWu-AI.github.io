# DSpark: 基于半自回归生成的置信度调度推测解码

> **论文全名**: DSpark: Confidence-Scheduled Speculative Decoding with Semi-Autoregressive Generation
>
> **作者**: DeepSeek 团队 + 北京大学（梁文锋署名）
>
> **发布时间**: 2026年6月27日
>
> **核心贡献**: 提出半自回归生成 + 置信度调度验证，在真实高并发推理服务中实现 60%-85% 的单用户生成速度提升

---

## 🎯 一句话总结

DSpark 不是新模型，而是一个**推理加速框架**——它让大模型在"猜答案"时猜得更准、验证时更省算力，从而在真实线上服务中显著提速。

---

## 🤔 为什么需要 DSpark？——先理解大模型的"慢"从哪来

### 大模型是怎么生成文字的？

大模型生成文字的方式叫**自回归（Autoregressive）**：每次只生成一个 token（可以理解为一个词或字），然后把这个 token 加到已有内容后面，再预测下一个 token。就像一个人**逐字写稿**，写完一个字才能写下一个。

这种方式的问题很明显：**内容越长，等待越久**。写一句短回复你可能感觉不到，但如果是生成长代码、长文章、复杂分析，生成速度就会直接影响体验。

### 什么是推测解码（Speculative Decoding）？

推测解码的思路很直观：**让一个轻量模型先快速"猜"出一段草稿，再让大模型一次性批改确认**。

打个比方：
- **没有推测解码**：像一个人逐字写稿，写完一个字才能写下一个
- **有推测解码**：像先让助手快速打出一小段草稿，再由主笔确认哪些内容能用

猜对的部分直接采用，猜错的部分重新生成。如果草稿猜得准，大模型一次就能确认多个 token，速度自然就快了。

---

## ⚡ DSpark 要解决的两个核心问题

### 问题一：并行草稿"越往后越容易猜偏"

草稿模型有两种生成方式：

| 类型 | 怎么工作 | 优点 | 缺点 |
|------|---------|------|------|
| **自回归草稿器** | 一个 token 一个 token 顺序生成 | 后面的 token 能参考前面的，序列连贯 | 草稿生成本身就慢 |
| **并行草稿器** | 一次 forward pass 同时生成一整段 | 快！所有位置同时出结果 | 后面的 token 不知道前面实际采样了什么 |

并行草稿器虽然快，但有一个**结构性缺陷**：每个位置的 token 是同时预测的，后面的 token 并不知道前面实际选了哪个词。

**举个直观的例子**：

上下文后面既可以接 "of course"，也可以接 "no problem"。这两个续写本身都合理。但如果每个位置独立预测，模型可能把不同续写路径混在一起，生成 **"of problem"** 或 **"no course"** 这种不伦不类的组合。

这种现象叫 **Multi-modal Collision（多模态碰撞）**——多个合理的续写方向被混在了一起。

后果就是：**draft block 越往后，token 越容易不连贯，也越容易被大模型拒绝**。这叫 **Suffix Decay（后缀接受率衰减）**——草稿越往后，越容易"掉队"。

### 问题二：验证不是"越多越好"

推测解码中，大模型对草稿的验证是**前缀式**的：只要中间某个 token 被拒绝，后面的 token 即使本身质量不错，也会被一起丢弃。

这意味着：如果草稿模型一次生成了很多 token，但后半段大概率会被拒绝，那把这些 token 全部送给大模型验证，就是在**浪费算力**。

在单个请求、低负载场景下，这种浪费也许不明显。但在**真实高并发服务**中，问题会被放大：

- 大模型的 **batch capacity**（同一轮推理中 GPU 能同时处理多少请求/token 的计算额度）是有限的
- 每多验证一个低价值 token，就可能**挤占其他用户请求**的计算资源
- 代码、数学这类结构化任务通常更容易被接受；开放聊天这种自由度更高的任务，后缀 token 更容易被拒绝

**所以，验证长度不应该固定，而应该根据 token 被接受的概率和系统负载动态决定。**

## 🔧 DSpark 的两大核心设计

### 设计一：半自回归生成——给并行草稿加一点"顺序感"

**核心思想**：保留并行生成的速度，同时让后面的 token 能感知前面已经生成的内容。

DSpark 不是让草稿模型完全回到一个 token 一个 token 的自回归生成，而是在并行生成的基础上，**引入一层很轻的顺序依赖**。

具体来说，DSpark 的草稿生成分两步：

```
第一步：并行主干（Parallel Backbone）
  → 一次 forward pass 快速生成整段 draft block（保留速度优势）

第二步：轻量顺序模块（Lightweight Sequential Head）
  → 在 draft block 内给后续 token 补充局部顺序信息
  → 让它们能参考前面已经采样出来的 token
```

**顺序模块的两种实现**：

| 方案 | 怎么工作 | 效果 | DSpark 选择 |
|------|---------|------|------------|
| **Markov Head** | 只看前一个已采样 token，用轻量转移偏置调整下一个 token 的概率 | 效果好、延迟低、部署简单 | ✅ 默认方案 |
| **RNN Head** | 记录更长的 block 内历史 | 理论表达力更强，但收益有限、部署复杂 | ❌ 不采用 |

继续用前面的例子理解 Markov Head：如果前一个 token 已经采样成 "of"，Markov head 就会让后续 token 更倾向于走向 "course" 这类更连贯的组合，而不是和另一条语义路径混在一起生成 "problem"。

**为什么选 Markov Head 而不是 RNN Head？** 这个选择很有工程意味：
- 对于生产级在线推理服务，额外模块不能只看效果提升
- 还要看是否足够轻、是否引入明显延迟、是否容易接入现有推理链路
- Markov Head 在效果、延迟和部署成本之间更均衡

**关键判断**：DSpark 不是放弃并行生成，也不是把草稿模型重新变慢，而是在并行生成之后**补上一层轻量顺序修正**。

### 设计二：置信度调度验证——验证多长，让数据和负载说了算

**核心思想**：不是所有草稿 token 都值得验证，验证长度应该根据 token 被接受的概率和系统负载动态决定。

DSpark 引入了三个关键组件：

#### 1. Confidence Head（置信度头）

一个轻量判断器，估计草稿 token 通过大模型验证的概率。

更准确地说，它预测的是 **Prefix Survival Probability（前缀存活概率）**：从第一个草稿 token 开始，连续通过验证并"活到当前位置"的概率。

为什么要预测这个值？因为验证是前缀式的——如果第 2 个 token 被拒绝，第 3、4、5 个 token 即使本身质量不错，也会被一起丢弃。所以第 5 个 token 是否值得验证，不只取决于它自己准不准，还取决于前面 1-4 个 token 能不能先通过。

#### 2. Hardware-Aware Prefix Scheduler（硬件感知前缀调度器）

结合两类信息，为每个请求动态选择验证长度：

```
输入信息：
  ├── Token 层面：prefix survival probability（前缀存活概率）
  └── 系统层面：engine throughput profile（推理引擎在不同 batch size 下的吞吐曲线）

输出：
  └── 每个请求的 verification length（验证长度）
```

调度逻辑：
- **低负载时**：目标模型还有空余计算能力 → 分配更长的验证预算，多验证一些高价值 token
- **高负载时**：batch capacity 更紧张 → 收紧验证长度，低置信 token 尽早剪掉，避免挤占其他请求

**核心变化**：verification length 不再是一个固定超参数，而是一个**随请求质量和系统负载变化的调度决策**。

#### 3. Sequential Temperature Scaling（顺序温度缩放）

对 confidence head 的输出做后处理校准，让预测概率更接近真实接受率。

为什么需要校准？如果模型给出的置信度只是"排序大致正确"但概率本身不可信，scheduler 就可能误判某些后缀 token 的收益，继续把 batch capacity 浪费在低通过率 token 上。

**在生产系统里，置信度不只是一个辅助分数，而是参与资源调度的决策信号。它必须足够稳定、足够可信。**

## 📊 实验结果

### 离线实验：DSpark 的草稿更容易被接受

在 Qwen3-4B、Qwen3-8B、Qwen3-14B 和 Gemma4-12B 等目标模型上评估，任务覆盖数学推理、代码生成和日常聊天。

对比对象：
- **Eagle3**：代表自回归草稿器
- **DFlash**：代表并行草稿器
- **DSpark**：在两者之间取更适合在线推理服务的折中

| 对比对象 | Qwen3-4B | Qwen3-8B | Qwen3-14B |
|---------|----------|----------|-----------|
| vs Eagle3 | +30.9% | +26.7% | +30.0% |
| vs DFlash | +16.3% | +18.4% | +18.3% |

> 以上为宏平均 accepted length 提升幅度

**关键发现**：DSpark 的收益不是来自"生成更多 token"，而是来自"生成出来的 token 更容易被接受"——它确实缓解了并行草稿器后缀不稳定的问题。

**任务差异**：数学和代码这类结构化任务更容易获得较高 accepted length，开放聊天任务更低。这不是模型优劣问题，而是任务分布本身不同——结构化任务有更明确的推理路径，草稿 token 更容易被接受。

### 线上部署：改善吞吐与交互速度的关系

DSpark 被部署到 DeepSeek-V4-Flash 和 DeepSeek-V4-Pro 的生产级在线推理服务系统中，与 MTP-1 baseline 对比。

| 模型 | 单用户生成速度提升 |
|------|------------------|
| V4-Flash | 60%–85% |
| V4-Pro | 57%–78% |

> 在匹配系统吞吐水平下的提升

**注意**：线上部署实验验证的不是"单个请求能不能更快"，而是**整个在线推理服务系统在真实流量下，能否在系统吞吐和用户可感知速度之间取得更好的平衡**。

- 在相同系统吞吐下，用户可以看到更快的生成速度
- 在更高交互速度要求下，系统仍然能维持更可用的并发能力
- 严格 SLA 点上的相对提升比例非常高，但需要谨慎理解（MTP-1 baseline 已接近能力边界，所以相对提升比例显得很大）

## 🧠 通俗类比总结

把 DSpark 想象成一个**高效的写作团队**：

| 角色 | 对应 DSpark 组件 | 做什么 |
|------|----------------|--------|
| **速记员** | 并行主干（Parallel Backbone） | 快速打出一整段草稿 |
| **校对员** | Markov Head | 快速扫一眼草稿，把明显不连贯的地方修正（比如 "of problem" → "of course"） |
| **质检员** | Confidence Head | 给每个字打分：这个字有多大可能通过主编审核 |
| **调度员** | Hardware-Aware Scheduler | 根据主编当前忙不忙，决定送多少草稿给主编审核 |
| **主编** | 目标大模型 | 最终审核确认，通过的直接采用，不通过的重新来 |

**调度员的智慧**：
- 主编不忙时 → 多送一些草稿过去审核，充分利用空闲时间
- 主编很忙时 → 只送最有把握的部分，别浪费主编精力
- 不同类型的稿件（代码 vs 聊天）→ 质检标准不同，送审策略也不同

## 💡 这篇论文真正值得关注的地方

DSpark 的核心贡献不只是"让推理更快"，而是**把推理加速从单纯的模型问题，推进到了系统级联合优化问题**：

1. **草稿模型不能只追求快**——生成的 token 必须足够容易被目标模型接受，否则长 draft block 只会带来更多无效候选
2. **验证不能只追求长**——目标模型的计算资源是在线推理服务系统里最关键的资源之一，低置信 token 的验证会直接影响系统吞吐
3. **调度策略必须理解系统负载**——同一个 token，低负载时可能值得验证，高负载时就未必划算

**评估推理加速方案的判断框架**（DSpark 给出的）：
- ✅ 生成的 draft token 最后有多少真的被接受
- ✅ 是否减少了无效 verification
- ✅ 在不同负载下是否还能维持系统吞吐
- ✅ 是否改善了用户可感知的生成速度
- ✅ 收益是否在真实在线推理服务系统中成立

---

## ⚠️ 局限性与未来方向

- DSpark 仍然需要先通过 parallel backbone 生成初始 draft block，对于一些本身接受率较低、难度较高的请求，draft-side cost 可能无法完全回收
- 未来可以探索 **difficulty-aware early exiting**，让低接受率请求尽早跳过不划算的 full-block drafting
- DSpark 的价值不在于提供"一劳永逸"的推理加速方案，而在于给出了一个**生产级推理优化样本**
